# 原文高亮与 Source 状态闪烁：根因分析报告

日期：2026-09-01

范围：`entrypoints/content.ts`、`entrypoints/sidepanel/App.tsx`、本地存储状态同步

问题等级：用户感知高；在旧实现中存在状态误判和偶发保存失败的风险

## 1. 结论摘要

这不是单纯的 CSS 闪烁，而是“异步 DOM 观察 + 全量重建高亮 + 持久化状态反馈”叠加造成的竞态问题。

核心原因有四个：

1. AI 网站是持续变化的单页应用，页面任意局部变化都会触发 `MutationObserver`。
2. 旧的 `refreshHighlights()` 每次刷新都会先解除全部高亮，再异步读取存储，然后重新包裹原文。
3. 高亮暂时定位不到时，旧实现立即把 `anchor.status` 写成 `unresolved`；写入又触发下一轮刷新。
4. 刷新函数没有“进行中锁”，两个异步刷新可以交错执行，互相解除或重建高亮。

因此，用户看到的表象是：原文短暂恢复成普通文本，随后重新变成高亮；卡片则在 `Source found` 和 `Source not found` 之间来回切换。真正的问题是把“页面当前某一瞬间还没渲染完”当成了“来源已经永久丢失”。

## 2. 用户现象与影响

### 2.1 原文闪烁

页面在流式输出、切换分支、滚动加载、插入工具栏或更新属性时，会产生 DOM mutation。扩展收到 mutation 后会调度高亮刷新。

旧流程中，高亮在等待 `loadState()` 期间已经被解除：

```text
MutationObserver
  → refreshHighlights()
  → unwrap all <mark>
  → await loadState()
  → locate text
  → surroundContents(<mark>)
```

`loadState()` 和文本定位之间的空窗期就是可见闪烁窗口。刷新越频繁、页面越忙，这个窗口出现得越多。

### 2.2 Source 状态闪烁

旧流程把每次定位结果直接映射为持久化状态：

```text
本轮暂时找不到
  → status = unresolved
  → chrome.storage.onChanged
  → 再次 refreshHighlights()
  → 页面恢复后找到
  → status = resolved
```

这里的 `unresolved` 混用了两种不同语义：

- 页面正在重绘，暂时没有可定位的节点；
- 原文确实被编辑、删除或变得无法唯一定位。

这两个状态不能在一次瞬时扫描中区分，但旧实现把它们当成同一个事实写入了存储。

### 2.3 clip 偶发失败

clip 操作也跨越了多个异步边界。用户点击按钮后，原页面可能重绘，导致：

- 当前 `Range` 的节点已经脱离 DOM；
- `createAnchor()` 或后续 `surroundContents()` 抛出 DOM 异常；
- clip 实际已经保存，但保存后的高亮操作失败，用户误以为整个 clip 失败；
- 极少数情况下，消息没有返回有效 response，旧代码直接访问 `response.type`，会产生二次异常；
- 用户连续点击时，可能同时发起多个 capture 请求。

这说明 clip 的“数据保存成功”和“页面高亮成功”原本没有被当作两个独立结果处理。

## 3. 详细触发链

一次典型的闪烁可以还原为以下事件序列：

```text
用户已有一个高亮 clip
        │
        ▼
AI 页面发生局部 React/流式 DOM 更新
        │
        ▼
MutationObserver 调度刷新
        │
        ▼
旧 refreshHighlights 先移除所有 <mark>
        │
        ├── 页面此时显示普通文本：原文闪烁
        │
        ▼
异步读取 storage，期间页面继续变化
        │
        ├── 本轮找不到 root 或 text segment
        │       │
        │       └── 写入 unresolved
        │               │
        │               └── storage.onChanged 再次调度刷新
        │
        ▼
下一轮页面已稳定，重新找到原文
        │
        └── 写入 resolved：卡片状态反向闪烁
```

此外，如果第二轮刷新在第一轮尚未完成时启动，两轮都操作同一批 `<mark>`，结果会进一步变得不可预测。

## 4. 根因分类

### A. 把“重建”当成“同步”

高亮是用户正在看的内容。对这类可见 UI，刷新应当尽量是无损、增量、幂等的更新。旧实现采用了先删除、再异步创建的方式，相当于把中间态直接暴露给用户。

### B. 没有区分稳定状态和过渡状态

页面 DOM 对第三方网站来说是 eventually consistent（最终一致）的：节点短暂不存在是正常现象。一次扫描失败只能说明“当前无法确认”，不能直接说明“来源不存在”。

### C. 异步任务只有 debounce，没有 coalescing/serialization

清除 timer 只能避免多个待执行 timer，不能阻止已经开始的异步函数并行运行。凡是会修改同一 DOM 区域的异步刷新，都需要进行中锁、版本号或取消机制。

### D. 把 live DOM 引用跨 await 保存

`Range`、`Node`、`HTMLElement` 都是活的 DOM 引用，不是稳定数据。它们跨越页面重绘或 `await` 后可能失效。用户输入应在异步边界之前转换成字符串、offset、message id 等可验证的数据。

### E. 失败边界不完整

保存、定位和视觉反馈是三个不同阶段。任一阶段失败都应该被捕获并清理局部副作用，不能让异常从事件回调中冒出，也不能因为高亮失败而掩盖“clip 已保存”的事实。

## 5. 本次修复落实的措施

### 5.1 高亮改为增量 reconcile

当前刷新会先读取状态，但不会在等待期间移除现有高亮。进入 DOM 修改阶段后：

- 已存在的高亮保留原节点，只更新颜色和主题属性；
- 只有不属于当前对话的旧标记才会移除；
- 新高亮定位失败不会先破坏已有内容；
- 多段文本包裹失败时，会清理本轮新建的局部标记。

这使得刷新从“先清空再重建”变成了幂等的增量同步。

### 5.2 高亮刷新串行化

刷新增加进行中 Promise 和 queued 标记。刷新期间的新请求不会再并发改 DOM，而是在当前任务结束后合并为下一轮刷新。

### 5.3 Source 状态增加确认窗口

当前实现不会因为一次扫描失败就写入 `unresolved`，而是要求连续多次确认，并经过约 1.2 秒的宽限期。页面重绘期间的短暂缺失会被视为过渡态，不会立即反映到卡片上。

### 5.4 clip 入口使用稳定 Range 并隔离阶段失败

当前实现会优先验证当前 Range 是否仍连接到 DOM，必要时使用仍有效的缓存 Range；捕获阶段增加了防重复执行、无 response 防护和异常捕获。clip 保存成功但高亮暂时失败时，会保留成功提示并安排后续恢复，而不是把整个操作判定为失败。

## 6. 可以沉淀为设计准则的规则

以下规则建议作为后续涉及 DOM、异步状态和第三方网站适配的代码评审清单。

### 规则 1：可见内容禁止使用“先删除、异步后重建”

对高亮、选区、滚动位置、输入内容等用户正在看的对象，更新必须满足：

- 先保留旧内容；
- 新内容准备好后再替换；
- 能增量更新就不要重建；
- 中间态不能短暂显示给用户。

### 规则 2：所有异步边界前都要快照用户输入

在 `await` 之前保存字符串和定位信息；不要在 `await` 之后继续依赖未验证的 `Range` 或 DOM 节点。任何 DOM 引用再次使用前都要检查 `isConnected`，并准备重新定位路径。

### 规则 3：debounce 不等于串行化

只要异步任务会修改同一资源，就必须至少具备以下一种机制：

- in-flight lock + queued rerun；
- generation/version 校验；
- AbortController 取消旧任务；
- 单一任务队列。

### 规则 4：第三方 DOM 的“暂时不存在”必须是 transient state

第三方网站的 DOM 扫描结果不应直接成为持久化事实。建议使用明确的状态机：

```text
unknown / resolving → resolved
unknown / resolving → temporarily-missing
temporarily-missing → resolved
temporarily-missing → unresolved（经过确认）
```

只有稳定确认后的 `unresolved` 才写入存储。

### 规则 5：派生状态写入必须有反馈回路保护

监听 `storage.onChanged` 的逻辑如果又会写回 storage，必须保证：

- 只在值真正变化时写入；
- 不把同一结果反复写回；
- 来源事件和派生事件可以区分；
- 写入失败不会触发无限重试。

### 规则 6：保存结果和视觉结果分离

一个用户动作至少要区分：

```text
capture persisted：数据是否已经保存
source resolved：原文当前能否定位
highlight rendered：页面是否已经显示高亮
```

三者不能互相覆盖。比如数据已保存但页面正在重绘时，应显示“已保存，稍后恢复高亮”，而不是报告保存失败。

### 规则 7：DOM 副作用必须可回滚

涉及多个文本节点的包裹操作不是原子的。实现时要记录本轮创建的节点；中途失败时只回滚本轮副作用，不能清理其他 clip 的标记。

### 规则 8：定位策略宁可不定位，也不要猜

message id、offset、前后文和唯一文本匹配应按可信度降级。重复文本无法唯一确认时保持 unresolved/temporarily-missing，不要为了消除状态提示而标到错误位置。

## 7. 后续测试建议

现有类型检查、58 个单测和生产构建已通过；但这类问题最终需要浏览器中的异步行为测试。建议补充以下场景：

- `loadState()` 延迟期间触发页面 DOM 更新，高亮不能消失；
- 两次 refresh 同时启动，最终只能有一份稳定高亮；
- 定位连续失败两次、成功一次，状态不能切换为 unresolved；
- 页面重绘导致 `Range` 脱离 DOM，clip 仍能从缓存 Range 或重新选择中正确处理；
- `surroundContents()` 在多段包裹中途抛错，不能留下半段高亮；
- capture response 为 `undefined` 或异常，页面显示可理解的失败提示；
- 用户在 capture 未完成前连续点击，不能创建重复 clip；
- ChatGPT 流式输出、Claude 消息更新、Gemini 滚动加载和主题切换期间进行上述测试。

建议在测试中使用一个“可控 DOM 页面”模拟器，而不是只依赖真实网站：通过手动延迟 storage、在两个 await 之间替换 message 节点、随机抛出包裹异常，可以稳定复现竞态。

## 8. 剩余风险与下一步

本次修复已经消除了最主要的视觉闪烁和状态反馈环。仍有两个长期维护点：

1. 1.2 秒确认窗口是防抖策略，不是网站语义知识。若某个平台未来出现更长的重绘窗口，应根据实际页面行为调整，或进一步改成“页面静止一段时间后再确认”。
2. 当前观察范围仍是较大的页面 subtree。后续可以让适配器提供更窄的 message root 观察范围，减少无关 mutation 触发刷新。

最终原则可以概括为：

> 不要把第三方页面的一次瞬时扫描，当成用户数据已经发生永久变化的证据；不要为了刷新而先破坏用户正在看的内容。
